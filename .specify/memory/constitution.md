# Spec-Kit 中文化專案章程

## 核心原則

### I. 客戶互動中文化（強制）

所有面向使用者的互動介面必須中文化為中文，包括但不限於：
- 指令說明文件（.md 檔案中的 `description` 欄位）
- 使用者提示資訊和錯誤訊息
- 文件範本中的說明文字
- 範例和註解文字

**理由**：提升中文使用者的使用體驗，降低理解門檻，確保工具的可及性。

### II. 程式穩定性優先（強制）

在中文化過程中必須確保程式正常運作：
- 技術性識別碼（變數名稱、函式名稱、檔案路徑）保持英文。
- 指令觸發關鍵字（如 `/speckit.specify`）可保持原樣或提供中文別名。
- 如果中文化會導致工具功能異常且無法規避，則該部分不進行中文化。
- 所有中文化都必須經過功能驗證。

**理由**：確保中文化不影響工具的核心功能，保持系統穩定性和可維護性。

### III. 結構化文件（強制）

中文化後的文件必須保持原有結構：
- 保留所有 Markdown 格式標記。
- 保持章節層級和標題結構。
- 保留程式碼區塊、表格等格式元素。
- 維護文件間的引用關係。

**理由**：確保文件的可讀性和工具的正常解析。

## 中文化標準

### 指令檔案中文化規則

1.  **YAML 檔頭**：`description` 欄位翻譯為中文。
2.  **章節標題**：翻譯為對應的中文標題。
3.  **說明文字**：所有面向使用者的說明文字翻譯為中文。
4.  **技術識別碼**：保持變數名稱、路徑、指令等技術識別碼為英文。
5.  **範例程式碼**：註解翻譯為中文，程式碼保持原樣。

### 範本檔案中文化規則

1.  **佔位符**：`[PLACEHOLDER]` 形式的佔位符可翻譯為 `[中文佔位符]`。
2.  **說明註解**：`<!-- 註解 -->` 中的內容翻譯為中文。
3.  **章節標題**：翻譯為中文。
4.  **範例文本**：翻譯為中文。

### 不進行中文化的內容

- 檔案路徑和檔案名稱
- 程式碼變數名稱和函式名稱
- JSON/YAML 的鍵名
- 命令列參數名稱
- Git 相關術語（如 `branch`、`commit`）
- 技術術語的標準英文縮寫（如 API、CLI、TDD）

## 品質保證

### 驗證流程

1.  **功能測試**：每次中文化後執行完整的工作流程進行驗證。
2.  **格式檢查**：確保 Markdown 格式正確。
3.  **一致性檢查**：術語翻譯保持一致。
4.  **文件審查**：檢查翻譯的準確性和可讀性。

### 術語對照表

建立標準術語對照表，確保翻譯一致性：
- Specification → 規格/規格說明
- Plan → 計畫/方案
- Task → 任務
- Implementation → 實作
- Constitution → 章程/原則
- Feature → 功能
- Requirement → 需求

## 治理

### 修訂流程

1.  所有章程修訂必須記錄版本變更。
2.  重大修改需要更新所有相關的範本和文件。
3.  中文化工作必須遵循此章程的所有原則。

### 合規性

- 所有 PR 都必須驗證中文化內容不影響功能。
- 必須保持原有的工作流邏輯不變。
- 複雜的修改需要提供詳細的影響分析。
