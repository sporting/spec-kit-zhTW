## 📋 指令用途

**將技術方案分解為可執行的任務清單**

---

## 使用者輸入

```text
$ARGUMENTS
```

在繼續之前，您**必須**考慮使用者輸入（如果不為空）。

## 執行流程

1. **設定**：從儲存庫根目錄執行 `.specify/scripts/bash/check-prerequisites.sh --json` 並解析 `FEATURE_DIR` 和 `AVAILABLE_DOCS` 清單。所有路徑必須是絕對路徑。對於參數中的單引號（例如 "I'm Groot"），請使用轉義語法：例如 `'I'\''m Groot'`（或者如果可能，請使用雙引號："I'm Groot"）。

2. **載入設計文件**：從 `FEATURE_DIR` 讀取：
   - **必要**：`plan.md`（技術棧、函式庫、結構）、`spec.md`（附有優先級的使用者故事）
   - **可選**：`data-model.md`（實體）、`contracts/`（API 端點）、`research.md`（決策）、`quickstart.md`（測試場景）
   - **注意**：並非所有專案都包含所有文件。請根據可用的內容產生任務。

3. **執行任務產生工作流程**（遵循範本結構）：
   - 載入 `plan.md` 並提取技術棧、函式庫、專案結構。
   - **載入 `spec.md` 並提取附有優先級的使用者故事（P1, P2, P3 等）。**
   - 如果 `data-model.md` 存在：提取實體 → 映射至使用者故事。
   - 如果 `contracts/` 存在：每個檔案 → 將端點映射至使用者故事。
   - 如果 `research.md` 存在：提取決策 → 產生設定任務。
   - **按使用者故事組織產生任務**：
     - **設定任務**（所有故事所需的共享基礎設施）。
     - **基礎任務**（在任何使用者故事開始前必須完成的前提條件）。
     - 對於每個使用者故事（按優先級順序 P1, P2, P3...）：
       - 將完成該故事所需的所有任務分組。
       - 包括特定於該故事的模型、服務、端點、UI 元件。
       - 標記哪些任務是 **[P] 可並行化**的。
       - 如果請求測試：包括特定於該故事的測試。
     - **完善/整合任務**（跨領域關注點）。
   - **測試是可選的**：僅當功能規格中明確要求或使用者要求 TDD 方法時，才產生測試任務。
   - **應用任務規則**：
     - 不同檔案 = 標記 **[P]** 用於並行。
     - 同一檔案 = 順序（無 **[P]**）。
     - 如果請求測試：測試在實作之前（TDD 順序）。
   - 按順序編號任務（T001, T002...）。
   - 產生顯示使用者故事完成順序的依賴關係圖。
   - 為每個使用者故事建立並行執行範例。
   - 驗證任務完整性（每個使用者故事都擁有所需的所有任務，且可獨立測試）。

4. **產生 `tasks.md`**：使用 `.specify/templates/tasks-template.md` 作為結構，並填入：
   - 來自 `plan.md` 的正確功能名稱。
   - **階段 1：設定任務**（專案初始化）。
   - **階段 2：基礎任務**（所有使用者故事的阻塞性前提條件）。
   - **階段 3+：每個使用者故事一個階段**（按 `spec.md` 中的優先級順序）。
     - 每個階段包括：故事目標、獨立測試標準、測試（如果請求）、實作任務。
     - 每個任務清晰的 **[Story]** 標籤（US1, US2, US3...）。
     - 可並行化任務的 **[P]** 標記。
     - 每個故事階段後的檢查點標記。
   - **最終階段：完善與跨領域關注點**。
   - 按執行順序編號的任務（T001, T002...）。
   - 每個任務的清晰檔案路徑。
   - 顯示故事完成順序的**依賴關係**章節。
   - 每個故事的**並行執行範例**。
   - **實作策略**章節（MVP 優先、增量交付）。

5. **報告**：輸出產生的 `tasks.md` 的路徑和摘要：
   - 總任務數。
   - 每個使用者故事的任務數。
   - 識別出的並行機會。
   - 每個故事的獨立測試標準。
   - 建議的 MVP 範圍（通常僅使用者故事 1）。

用於任務產生的上下文：`$ARGUMENTS`

`tasks.md` 應該要能立即執行——每個任務都必須足夠具體，以便 LLM 可以在沒有額外上下文的情況下完成它。

## 任務產生規則

**重要**：測試是可選的。僅當使用者在功能規格中明確要求測試或 TDD 方法時，才產生測試任務。

**關鍵**：任務必須按使用者故事組織，以實現獨立的實作和測試。

1.  **從使用者故事 (`spec.md`)** - 主要組織方式：
    -   每個使用者故事（P1, P2, P3...）都有自己的階段。
    -   將所有相關元件映射到其故事：
        -   該故事所需的模型。
        -   該故事所需的服務。
        -   該故事所需的端點/UI。
        -   如果請求測試：特定於該故事的測試。
    -   標記故事依賴關係（大多數故事應為獨立的）。

2.  **從合約 (`contracts`)**：
    -   將每個合約/端點 → 映射到它所服務的使用者故事。
    -   如果請求測試：每個合約 → 在該故事階段的實作之前，進行合約測試任務 **[P]**。

3.  **從資料模型 (`data-model.md`)**：
    -   將每個實體 → 映射到需要它的使用者故事。
    -   如果實體服務於多個故事：將其放在最早的故事或設定階段。
    -   關聯 → 在適當故事階段的服務層任務。

4.  **從設定/基礎設施**：
    -   共享基礎設施 → **設定階段**（階段 1）。
    -   基礎/阻塞性任務 → **基礎階段**（階段 2）。
        -   範例：資料庫結構設定、身份驗證框架、核心函式庫、基本組態。
        -   這些必須在任何使用者故事實作之前完成。
    -   故事特定的設定 → 在該故事的階段內。

5.  **排序**：
    -   **階段 1：設定**（專案初始化）。
    -   **階段 2：基礎**（阻塞性前提條件 - 必須在使用者故事之前完成）。
    -   **階段 3+：按優先級順序的使用者故事**（P1, P2, P3...）。
        -   在每個故事內：測試（如果請求）→ 模型 → 服務 → 端點 → 整合。
    -   **最終階段：完善與跨領域關注點**。
    -   每個使用者故事階段都應該是一個完整的、可獨立測試的增量。
