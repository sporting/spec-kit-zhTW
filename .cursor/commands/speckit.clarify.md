## 📋 指令用途

**解決規格中的模糊和歧義問題**

---

## 使用者輸入

```text
$ARGUMENTS
```

在繼續之前，您**必須**考慮使用者輸入（如果不為空）。

## 執行流程

目標：偵測並減少活動功能規格中的歧義或缺失決策點，並將澄清直接記錄在規格文件中。

注意：此澄清工作流程預期在呼叫 `/speckit.plan` 之前運行（並完成）。如果使用者明確聲明他們跳過澄清（例如探索性嘗試），您可以繼續，但必須警告下游返工風險會增加。

執行步驟：

1. 從倉庫根目錄**一次性**運行 `.specify/scripts/bash/check-prerequisites.sh --json --paths-only`（組合 `--json --paths-only` 模式 / `-Json -PathsOnly`）。解析最小 JSON 負載字段：
   - `FEATURE_DIR`
   - `FEATURE_SPEC`
   - （可選捕獲 `IMPL_PLAN`、`TASKS` 用於未來鏈式流程。）
   - 如果 JSON 解析失敗，中止並指示使用者重新運行 `/speckit.specify` 或驗證功能分支環境。
   - 對於參數中的單引號（如"I'm Groot"），使用轉義語法：例如 'I'\''m Groot'（或者如果可能使用雙引號："I'm Groot"）。

2. 載入目前規格文件。使用此分類法執行結構化的歧義和覆蓋率掃描。對於每個類別，標記狀態：清晰 / 部分 / 缺失。產生用於優先排序的內部覆蓋率映射（除非不會提出問題，否則不輸出原始映射）。

   功能範圍和行為：
   - 核心使用者目標和成功標準
   - 明確的範圍外聲明
   - 使用者角色/人物角色區分

   領域和資料模型：
   - 實體、屬性、關係
   - 身份和唯一性規則
   - 生命週期/狀態轉換
   - 資料量/規模假設

   互動和使用者體驗流程：
   - 關鍵使用者旅程/序列
   - 錯誤/空/載入狀態
   - 可訪問性或本地化說明

   非功能品質屬性：
   - 性能（延遲、吞吐量目標）
   - 可擴展性（水平/垂直、限制）
   - 可靠性和可用性（正常運行時間、恢復期望）
   - 可觀測性（日誌記錄、指標、追蹤訊號）
   - 安全和隱私（身份驗證、授權、加密、資料保留、合規性）

   整合和依賴關係：
   - 外部系統、API、服務依賴
   - 向後兼容性或遷移路徑
   - 環境/部署約束

3. 從覆蓋率映射中，選擇最多 5 個具有最高影響/風險的澄清問題。優先級：
   - 範圍歧義（例如多個解釋）
   - 缺失的關鍵決策（例如身份驗證方法、資料保留）
   - 性能/安全性差距
   - 使用者體驗細節中的漏洞

4. 對於每個選定的問題（最多 5 個），向使用者提出一個結構化問題，使用此格式：

   ```markdown
   ## 澄清問題 [N]：[主題]
   
   **規格引用**：[引用相關章節或需求]
   
   **需要澄清的內容**：[具體問題]
   
   **建議選項**：
   
   | 選項 | 答案 | 影響 |
   |------|------|------|
   | A    | [第一個建議答案] | [這對功能意味著什麼] |
   | B    | [第二個建議答案] | [這對功能意味著什麼] |
   | C    | [第三個建議答案] | [這對功能意味著什麼] |
   | 自訂 | 提供您自己的答案 | [解釋如何提供自訂輸入] |
   
   **您的選擇**：_[等待使用者回覆]_
   ```

5. 等待使用者回應所有問題（例如：「Q1: A, Q2: 自訂 - [詳情], Q3: B」）。

6. 對於每個答案：
   - 將澄清內容編碼回規格文件的適當章節
   - 刪除任何 `[需要澄清]` 標記（如果存在）
   - 在假設條件章節記錄決策理由（如果相關）

7. 更新品質檢查清單（`FEATURE_DIR/checklists/requirements.md`），將「沒有遺留的 [需要澄清] 標記」標記為通過。

8. 向使用者報告澄清摘要：
   - 已解決的問題數量
   - 更新的規格章節
   - 下一步建議（通常是 `/speckit.plan`）

## 關鍵規則

- 最多 5 個問題 - 保持重點和可操作性
- 問題必須具體且有針對性，而不是開放式的
- 提供建議答案以加快決策
- 直接更新規格文件，不要建立單獨的文件
- 如果沒有重大歧義，通知使用者規格已經清晰，可以直接進行 `/speckit.plan`
