## 📋 指令用途

**將功能需求轉化為清晰的規格文件**

---

## 使用者輸入

```text
$ARGUMENTS
```

在繼續之前，您**必須**考慮使用者輸入（如果不為空）。

## 執行流程

使用者在觸發訊息中在 `/speckit.specify` 之後輸入的文本**就是**功能描述。假設您在本對話中總是​​可以獲得它，即使下面字面上顯示 `$ARGUMENTS`。除非使用者提供了空指令，否則不要要求使用者重複。

根據該功能描述，執行以下操作：

1. 從倉庫根目錄運行腳本 `.specify/scripts/bash/create-new-feature.sh --json "$ARGUMENTS"` 並解析其 JSON 輸出以獲取 BRANCH_NAME 和 SPEC_FILE。所有檔案路徑必須是絕對路徑。
  **重要**：您只能運行此腳本一次。JSON 在終端輸出中提供 - 始終參考它以獲取您要查找的實際內容。對於參數中的單引號（如"I'm Groot"），使用轉義語法：例如 'I'\''m Groot'（或者如果可能使用雙引號："I'm Groot"）。
2. 載入 `.specify/templates/spec-template.md` 以了解必需的章節。

3. 按以下執行流程操作：

    1. 從輸入解析使用者描述
       如果為空：錯誤 "未提供功能描述"
    2. 從描述中提取關鍵概念
       識別：參與者、操作、資料、約束
    3. 對於不清楚的方面：
       - 基於上下文和行業標準做出明智的猜測
       - 僅在以下情況下用 [需要澄清: 具體問題] 標記：
         - 選擇會顯著影響功能範圍或使用者體驗
         - 存在具有不同含義的多種合理解釋
         - 不存在合理的預設值
       - **限制：最多 3 個 [需要澄清] 標記**
       - 按影響優先排序澄清：範圍 > 安全/隱私 > 使用者體驗 > 技術細節
    4. 填寫使用者場景和測試章節
       如果沒有清晰的使用者流程：錯誤 "無法確定使用者場景"
    5. 產生功能需求
       每個需求必須可測試
       對未指定的細節使用合理的預設值（在假設條件章節記錄假設）
    6. 定義成功標準
       建立可衡量的、與技術無關的成果
       包括定量指標（時間、性能、數量）和定性度量（使用者滿意度、任務完成）
       每個標準必須在不了解實作細節的情況下可驗證
    7. 識別關鍵實體（如果涉及資料）
    8. 返回：成功（規格準備好進行規劃）

4. 使用範本結構將規格寫入 SPEC_FILE，用從功能描述（參數）派生的具體細節替換佔位符，同時保留章節順序和標題。

5. **規格品質驗證**：編寫初始規格後，根據品質標準進行驗證：

   a. **建立規格品質檢查清單**：在 `FEATURE_DIR/checklists/requirements.md` 使用檢查清單範本結構產生檢查清單檔案，包含以下驗證項：
   
      ```markdown
      # 規格品質檢查清單：[功能名稱]
      
      **目的**：在進入規劃階段前驗證規格的完整性和品質
      **建立日期**：[日期]
      **功能**：[連結到 spec.md]
      
      ## 內容品質
      
      - [ ] 沒有實作細節（語言、框架、API）
      - [ ] 專注於使用者價值和業務需求
      - [ ] 為非技術利害關係人編寫
      - [ ] 所有必填章節已完成
      
      ## 需求完整性
      
      - [ ] 沒有遺留的 [需要澄清] 標記
      - [ ] 需求可測試且明確
      - [ ] 成功標準可衡量
      - [ ] 成功標準與技術無關（無實作細節）
      - [ ] 所有驗收場景已定義
      - [ ] 邊界情況已識別
      - [ ] 範圍界限清晰
      - [ ] 依賴關係和假設條件已識別
      
      ## 功能就緒度
      
      - [ ] 所有功能需求都有明確的驗收標準
      - [ ] 使用者場景覆蓋主要流程
      - [ ] 功能滿足成功標準中定義的可衡量成果
      - [ ] 規格中沒有洩露實作細節
      
      ## 備註
      
      - 標記為未完成的項目需要在 `/speckit.clarify` 或 `/speckit.plan` 之前更新規格
      ```
   
   b. **運行驗證檢查**：對照每個檢查清單項審查規格：
      - 對於每個項，確定它是通過還是失敗
      - 記錄發現的具體問題（引用相關規格章節）
   
   c. **處理驗證結果**：
      
      - **如果所有項都通過**：標記檢查清單為完成並繼續步驟 6
      
      - **如果項目失敗（不包括 [需要澄清]）**：
        1. 列出失敗的項目和具體問題
        2. 更新規格以解決每個問題
        3. 重新運行驗證直到所有項通過（最多 3 次迭代）
        4. 如果 3 次迭代後仍然失敗，在檢查清單備註中記錄剩餘問題並警告使用者
      
      - **如果 [需要澄清] 標記仍存在**：
        1. 從規格中提取所有 [需要澄清: ...] 標記
        2. **限制檢查**：如果存在超過 3 個標記，只保留 3 個最關鍵的（按範圍/安全/使用者體驗影響），並對其餘部分做出明智的猜測
        3. 對於每個需要澄清的內容（最多 3 個），以此格式向使用者呈現選項：
        
           ```markdown
           ## 問題 [N]：[主題]
           
           **上下文**：[引用相關規格章節]
           
           **我們需要知道的**：[需要澄清標記中的具體問題]
           
           **建議答案**：
           
           | 選項 | 答案 | 影響 |
           |------|------|------|
           | A    | [第一個建議答案] | [這對功能意味著什麼] |
           | B    | [第二個建議答案] | [這對功能意味著什麼] |
           | C    | [第三個建議答案] | [這對功能意味著什麼] |
           | 自訂 | 提供您自己的答案 | [解釋如何提供自訂輸入] |
           
           **您的選擇**：_[等待使用者回覆]_
           ```
        
        4. **關鍵 - 表格格式**：確保 markdown 表格格式正確：
           - 使用一致的間距，管道符對齊
           - 每個單元格內容周圍應有空格：`| 內容 |` 而不是 `|內容|`
           - 表頭分隔符必須至少有 3 個破折號：`|------|`
           - 測試表格在 markdown 預覽中正確渲染
        5. 依次為問題編號（Q1、Q2、Q3 - 最多 3 個）
        6. 在等待回覆之前一起呈現所有問題
        7. 等待使用者回答所有問題的選擇（例如：「Q1: A, Q2: 自訂 - [詳情], Q3: B」）
        8. 透過將每個 [需要澄清] 標記替換為使用者選擇或提供的答案來更新規格
        9. 在所有澄清解決後重新運行驗證
   
   d. **更新檢查清單**：每次驗證迭代後，使用目前通過/失敗狀態更新檢查清單檔案

6. 報告完成情況，包括分支名稱、規格檔案路徑、檢查清單結果以及下一階段的準備情況（`/speckit.clarify` 或 `/speckit.plan`）。

**注意**：腳本在寫入前建立並檢出新分支並初始化規格檔案。

## 通用指南

## 快速指南

- 專注於**做什麼（WHAT）**和**為什麼（WHY）**
- 避免實作方式（HOW）（無技術棧、API、程式碼結構）
- 為業務利害關係人編寫，而不是開發者
- 不要建立任何嵌入在規格中的檢查清單。那將是單獨的指令。

### 章節要求

- **必填章節**：每個功能都必須完成
- **可選章節**：僅在與功能相關時包含
- 當章節不適用時，完全刪除它（不要留下"N/A"）

### 對於 AI 產生

從使用者提示建立此規格時：

1. **做出明智的猜測**：使用上下文、行業標準和常見模式來填補空白
2. **記錄假設**：在假設條件章節記錄合理的預設值
3. **限制澄清**：最多 3 個 [需要澄清] 標記 - 僅用於關鍵決策：
   - 顯著影響功能範圍或使用者體驗
   - 具有不同含義的多種合理解釋
   - 缺乏任何合理的預設值
4. **優先排序澄清**：範圍 > 安全/隱私 > 使用者體驗 > 技術細節
5. **像測試人員一樣思考**：每個模糊的需求都應該未通過「可測試且明確」的檢查清單項
6. **常見需要澄清的領域**（僅在不存在合理預設值時）：
   - 功能範圍和邊界（包含/排除特定用例）
   - 使用者類型和權限（如果可能存在多個衝突的解釋）
   - 安全/合規要求（在法律/財務上重要時）
   
**合理預設值的範例**（不要詢問這些）：

- 資料保留：該領域的行業標準實踐
- 性能目標：標準 Web/行動應用期望，除非另有說明
- 錯誤處理：具有適當回退的使用者友善訊息
- 身份驗證方法：Web 應用的標準基於會話或 OAuth2
- 整合模式：RESTful API，除非另有說明

### 成功標準指南

成功標準必須：

1. **可衡量**：包括具體指標（時間、百分比、計數、比率）
2. **與技術無關**：不提及框架、語言、資料庫或工具
3. **以使用者為中心**：從使用者/業務角度描述結果，而不是系統內部
4. **可驗證**：可以在不了解實作細節的情況下測試/驗證

**好的範例**：

- "使用者可以在 3 分鐘內完成結帳"
- "系統支援 10,000 個並發使用者"
- "95% 的搜尋在 1 秒內返回結果"
- "任務完成率提高 40%"

**不好的範例**（以實作為中心）：

- "API 響應時間低於 200 毫秒"（太技術化，使用"使用者即時看到結果"）
- "資料庫可以處理 1000 TPS"（實作細節，使用面向使用者的指標）
- "React 組件高效渲染"（特定於框架）
- "Redis 快取命中率高於 80%"（特定於技術）
