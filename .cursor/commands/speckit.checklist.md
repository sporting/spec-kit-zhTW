## 📋 命令用途

**產生需求品質驗證清單**

---

## 检查清单的目的："需求的单元测试"

**關鍵概念**：檢查清單是**需求編寫的單元測試** - 它們驗證給定領域中需求的品質、清晰度和完整性。

**不是用于验证/测试**：
- ❌ 不是"驗證按鈕點擊是否正確"
- ❌ 不是"測試錯誤處理是否工作"
- ❌ 不是"確認 API 返回 200"
- ❌ 不是檢查程式碼/實作是否匹配規範

**用于需求质量验证**：
- ✅ "是否為所有卡片類型定義了視覺層次需求？"（完整性）
- ✅ "'突顯'是否用具體的大小/位置量化？"（清晰度）
- ✅ "所有互動元素的懸停狀態需求是否一致？"（一致性）
- ✅ "是否定義了鍵盤導航的可及性需求？"（覆蓋率）
- ✅ "規範是否定義了標誌圖片載入失敗時的情況？"（邊界情況）

**比喻**：如果您的規範是用英語編寫的程式碼，檢查清單就是它的單元測試套件。您正在測試需求是否編寫良好、完整、明確並準備好實作 - 而不是實作是否有效。

## 用户输入

```text
$ARGUMENTS
```

在繼續之前，您**必須**考慮使用者輸入（如果不為空）。

## 执行步骤

1. **设置**：從儲存庫根目錄執行 `.specify/scripts/bash/check-prerequisites.sh --json` 並解析 JSON 以獲取 `FEATURE_DIR` 和 `AVAILABLE_DOCS` 列表。
   - 所有文件路徑必須是絕對路徑。
   - 對於參數中的單引號（如"I'm Groot"），使用轉義語法：例如 'I'\''m Groot'（或者如果可能使用雙引號："I'm Groot"）。

2. **澄清意图（动态）**：從使用者的措辭 + 從 spec/plan/tasks 提取的信號中派生最多三個初始上下文澄清問題。它們必須：
   - 從使用者的措辭 + 從 spec/plan/tasks 提取的信號生成
   - 僅詢問實質性改變檢查清單內容的資訊
   - 如果在 `$ARGUMENTS` 中已經明確則單獨跳過
   - 優先考慮精確性而非廣度

   生成演算法：
   1. 提取信號：功能領域關鍵詞（例如身份驗證、延遲、使用者體驗、API）、風險指標（"關鍵"、"必須"、"合規"）、利益相關者提示（"QA"、"審查"、"安全團隊"）和明確的交付成果（"無障礙"、"回滾"、"合約"）。
   2. 將信號聚類到候選關注領域（最多 4 個），按相關性排名。
   3. 識別可能的受眾和時機（作者、審閱者、QA、發布），如果不明確。
   4. 檢測缺失的維度：範圍廣度、深度/嚴格性、風險重點、排除邊界、可衡量的驗收標準。
   5. 從這些原型中選擇問題進行表述：
      - 範圍細化（例如"這應該包括與 X 和 Y 的整合接觸點還是僅限於本地模組正確性？"）
      - 風險優先級（例如"這些潛在風險領域中哪些應該接受強制門控檢查？"）
      - 深度校準（例如"這是輕量級的提交前健全性列表還是正式的發布門控？"）
      - 受眾框架（例如"這將僅由作者使用還是在 PR 審查期間由同行使用？"）
      - 邊界排除（例如"我們應該在本輪中明確排除效能調優項目嗎？"）
      - 場景類差距（例如"未檢測到恢復流程 - 回滾/部分失敗路徑是否在範圍內？"）

   問題格式規則：
   - 如果呈現選項，生成包含列的緊湊表：選項 | 候選 | 為什麼重要
   - 最多限制 A–E 選項；如果自由形式答案更清晰則省略表
   - 永遠不要要求使用者重述他們已經說過的內容
   - 如果使用者的請求已經具體（例如"效能檢查清單"），跳過模糊的問題

3. **等待用户响应**（如果提出了问题）：
   - 解析答案（例如"A"、"選項 B"、"自訂：..."）
   - 如果使用者說"跳過"或"預設"，使用從規範/計畫推斷的合理預設值
   - 不要重複提問

4. **加载相关上下文**：
   - 讀取 `spec.md`：需求、使用者故事、成功標準
   - 讀取 `plan.md`（如果存在）：技術上下文、架構、元件
   - 讀取 `tasks.md`（如果存在）：實作細節、階段
   - 讀取 `.specify/memory/constitution.md`：強制原則、品質標準

5. **检查清单生成**：
   - 建立檔案：`FEATURE_DIR/checklists/[檢查清單名稱].md`
   - 使用此結構：

     ```markdown
     # [檢查清單名稱]：[功能名稱]

     **目的**：[從使用者意圖派生的 1-2 句話目的]
     **建立日期**：[日期]
     **功能**：[連結到 spec.md]
     **受眾**：[作者/審閱者/QA/團隊]

     ## [類別 1 名稱]

     - [ ] [檢查項 1 - 作為問題表述，針對需求品質]
     - [ ] [檢查項 2]
     - [ ] [檢查項 3]

     ## [類別 2 名稱]

     - [ ] [檢查項 4]
     - [ ] [檢查項 5]

     ## [類別 N 名稱]

     - [ ] [檢查項 N]

     ## 備註

     [任何上下文、例外或指導]
     ```

6. **检查清单内容规则**：

   **每個檢查項必須**：
   - 是一個問題（"是否..."、"做..."），而不是陳述
   - 測試需求品質，而不是實作驗證
   - 具體且可操作（避免"考慮..."、"思考關於..."）
   - 可以用"是"或"否"回答（或"N/A"，如果適用）
   - 引用規範/計畫中的具體元素，如果相關

   **好的檢查項範例**：
   - ✅ "是否為每個使用者角色定義了明確的權限邊界？"
   - ✅ "每個錯誤場景是否指定了具體的使用者回饋？"
   - ✅ "效能目標是否以可衡量的指標量化（例如 <100ms）？"
   - ✅ "所有 API 端點是否記錄了預期的錯誤代碼？"

   **不好的檢查項範例**：
   - ❌ "考慮邊界情況"（太模糊）
   - ❌ "驗證登入工作"（這是測試，不是需求檢查）
   - ❌ "程式碼遵循最佳實踐"（這是程式碼審查，不是規範驗證）
   - ❌ "測試通過"（這是驗證，不是需求品質）

7. **类别生成**：
   - 根據功能領域和使用者意圖建立 3-7 個類別
   - 常見類別（僅在相關時使用）：
     - 功能完整性
     - 使用者體驗清晰度
     - 錯誤和邊界情況
     - 效能和可擴展性
     - 安全和隱私
     - 可及性
     - 資料完整性
     - 整合和依賴關係
   - 每個類別 3-8 個檢查項（避免過長的列表）

8. **报告完成**：
   - 輸出：`FEATURE_DIR/checklists/[檢查清單名稱].md`
   - 摘要：總檢查項數、類別數
   - 下一步：如何使用檢查清單驗證規範/計畫

## 关键规则

- **品質，而不是驗證**：檢查清單測試需求品質，而不是實作正確性
- **具體且可操作**：每個項目都必須清晰且可檢查
- **上下文感知**：根據功能領域、風險和受眾客製化
- **適當的大小**：足夠全面以有用，但不會壓倒性（20-40 項）
- **連結到規範**：檢查項應該引用規範/計畫中的具體元素

## 示例用途

**使用者請求**："為登入功能建立安全檢查清單"

**生成的检查清单应该验证**：
- ✅ 規範是否定義了密碼複雜性要求？
- ✅ 身份驗證失敗場景是否有明確的使用者回饋？
- ✅ 會話管理生命週期是否已記錄？
- ✅ 速率限制規則是否已指定？

**而不是**：
- ❌ 驗證密碼雜湊是否正常工作（這是測試）
- ❌ 確認 SQL 注入得到防禦（這是安全審查）
