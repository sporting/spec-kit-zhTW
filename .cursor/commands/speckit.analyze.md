## 📋 命令用途

**檢查規範、計畫、任務的一致性**

---

## 用户输入

```text
$ARGUMENTS
```

在繼續之前，您**必須**考慮使用者輸入（如果不為空）。

## 目标

在實作之前識別三個核心文件（`spec.md`、`plan.md`、`tasks.md`）之間的不一致性、重複、歧義和未充分說明的項目。此指令必須僅在 `/tasks` 成功生成完整的 `tasks.md` 之後執行。

## 操作约束

**嚴格只讀**：**不要**修改任何文件。輸出結構化的分析報告。提供可選的修復計畫（使用者必須明確批准後才能手動呼叫任何後續編輯指令）。

**章程權威**：專案章程（`.specify/memory/constitution.md`）在此分析範圍內是**不可協商的**。章程衝突自動為關鍵問題，需要調整規範、計畫或任務——而不是稀釋、重新解釋或默默忽略原則。如果原則本身需要更改，則必須在 `/analyze` 之外的單獨、明確的章程更新中進行。

## 执行步骤

### 1. 初始化分析上下文

從儲存庫根目錄執行一次 `.specify/scripts/bash/check-prerequisites.sh --json --require-tasks --include-tasks` 並解析 JSON 以獲取 `FEATURE_DIR` 和 `AVAILABLE_DOCS`。派生絕對路徑：

- SPEC = FEATURE_DIR/spec.md
- PLAN = FEATURE_DIR/plan.md
- TASKS = FEATURE_DIR/tasks.md

如果缺少任何必需文件，則中止並顯示錯誤訊息（指示使用者執行缺少的先決條件指令）。
對於參數中的單引號（如"I'm Groot"），請使用轉義語法：例如 `'I'\''m Groot'`（或者如果可能，請使用雙引號："I'm Groot"）。

### 2. 加载文档（渐进式披露）

僅從每個文件載入最少的必要上下文：

**从 spec.md：**

- 概述/上下文
- 功能需求
- 非功能需求
- 使用者故事
- 邊界情況（如果存在）

**从 plan.md：**

- 架構/技術棧選擇
- 資料模型（如果定義）
- 合約/端點（如果定義）
- 章程檢查/門控（如果存在）
- 研究決策（如果存在）

**从 tasks.md：**

- 任務階段（設定、基礎、使用者故事、完善）
- 任務 ID、描述、檔案路徑
- 並行標記 [P]
- 依賴關係

**从 constitution.md：**

- 核心原則
- 強制規則
- 品質標準

### 3. 执行多维一致性检查

執行以下檢查，為每個檢查建立問題清單：

#### A. 规范-计划对齐

- 規範中的每個功能需求是否在計畫中有對應的設計？
- 計畫中是否引入了規範中未請求的功能？
- 非功能需求（效能、安全性）是否在計畫的技術選擇中解決？

#### B. 计划-任务对齐

- 計畫中的每個元件（模型、服務、端點）是否在任務中有實作任務？
- 任務是否引入了計畫中未定義的檔案或元件？
- 任務順序是否尊重計畫的依賴關係？

#### C. 规范-任务对齐

- 每個使用者故事是否在任務中有完整的實作路徑？
- 任務是否按規範中定義的優先級（P1、P2、P3）排序？
- 邊界情況是否在任務中有相應的處理？

#### D. 宪章合规性

- 計畫和任務是否遵守章程中定義的所有強制原則？
- 是否有違反品質標準的情況（例如跳過測試、缺少文件）？
- 技術選擇是否符合章程約束？

#### E. 完整性检查

- 是否有孤立的需求（在規範中但未在計畫或任務中）？
- 是否有未映射的任務（未追溯到任何規範需求）？
- 關鍵領域（錯誤處理、日誌記錄、安全性）是否被涵蓋？

#### F. 质量和可测试性

- 每個使用者故事是否有明確的驗收標準？
- 關鍵功能是否有測試任務（如果章程要求 TDD）？
- 成功標準是否可透過任務驗證？

### 4. 问题分类和优先级

為每個發現的問題分配：

- **嚴重程度**：
  - 🔴 **關鍵**：章程違規、缺失的核心需求、阻塞性依賴關係
  - 🟡 **重要**：不一致性、歧義、品質差距
  - 🟢 **次要**：最佳化機會、文件改進

- **類別**：
  - 一致性問題
  - 完整性差距
  - 章程違規
  - 品質關注
  - 依賴關係問題

### 5. 生成分析报告

輸出結構化報告：

```markdown
# 一致性分析報告：[功能名稱]

**分析日期**：[日期]
**文件版本**：spec.md、plan.md、tasks.md
**章程版本**：[從 constitution.md]

## 執行摘要

- 總問題數：[數量]
  - 關鍵：[數量]
  - 重要：[數量]
  - 次要：[數量]
- 整體評估：✅ 準備實作 / ⚠ 需要注意 / 🔴 阻塞問題

## 關鍵問題 🔴

[列出所有關鍵問題及其上下文]

## 重要問題 🟡

[列出重要問題]

## 次要問題 🟢

[列出次要問題]

## 推薦修復計畫

[如果有問題，提出分階段的修復計畫]

階段 1：解決關鍵問題
階段 2：解決重要問題
階段 3：考慮次要改進

## 下一步

- 如果沒有關鍵問題：繼續 `/implement`
- 如果有關鍵問題：在繼續之前解決它們
```

### 6. 用户交互

- 如果發現關鍵問題：警告使用者並建議在實作前解決
- 如果僅有次要問題：通知使用者可以繼續，但建議改進
- 如果沒有問題：祝賀並確認準備實作

## 关键规则

- **只讀操作**：不修改任何文件
- **章程優先**：章程違規總是關鍵問題
- **全面檢查**：涵蓋所有三個文件的所有方面
- **可操作的輸出**：每個問題都應包含具體的修復建議
- **尊重使用者決策**：提供建議，但讓使用者決定是否繼續
